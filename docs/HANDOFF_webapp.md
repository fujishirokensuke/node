## 1. プロジェクトの思想(アプリ設計の最上位原則)

ユーザー本人の言葉(2026/5/31):

> 「ダイエット意識しすぎずに、ありのままに淡々と体重記録として食事内容をクセにすることを、一生のものにしたい」

- 目的は体重を落とすことではなく「**記録し続ける人間になる**」こと
- アプリは**ジャッジしない記録係**であること。評価・説教・ゲーミフィケーションの押し付けをしない
- 「ダメな日の報告」を歓迎する設計(欠測日を赤く責め立てない、そっと空白にする)
- 数値目標はあるが、UIは「淡々と」が基調

### ユーザーが自己言語化した過去の崩壊パターン(重要)

```
痩せ始める → 嬉しい → 「もっと痩せよう」モード → 運動・食事を厳しくする
→ お菓子が静かに増える → 報告が後ろめたくなる → 測定をやめる
→ 静かに戻る → 気づいたら78kg
```

アプリはこのパターンを**構造的に防ぐ**:
- 順調な時に「もっとやろう」と煽らない
- 欠測後の再開ハードルを最小化(「おかえり」程度、詰めない)
- 週平均・月平均を主指標にして単日の数値に一喜一憂させない

## 3. 計測の重要仕様(必ず実装)

### 3.1 体重計2台問題

| 機種 | 場所 | 体脂肪率 | 特性 |
|---|---|---|---|
| 秋谷 | 秋谷の家 | あり | 体組成計。**堀内より約+1.3〜1.6kg高く出る** |
| 堀内 | 堀内の家 | なし | 通常体重計。**ユーザーはこちらを「現実」として採用したい** |

- 推定機種差: **+1.5kg(秋谷が高い)** ※中央値。同日両機種計測が取れたら更新する
- **全データは機種タグ付きで保存**し、表示時に堀内基準へ換算統一する
  - 堀内実測 → そのまま
  - 秋谷実測 → -1.5kg で堀内換算(換算値であることを小さく表示)
- 換算係数は設定画面で変更可能にする(将来精緻化するため)

### 3.2 計測条件

- 起床後・トイレ後・**朝食前**・シャワー前
- パンツ or 全裸
- 体脂肪率の単日変動は水分の影響が大きく無意味 → **UIでは週平均・月平均を主表示**

## 5. 現行ルール(B運用、2026/6/29開始)

アプリはこれらの達成状況を**淡々と可視化**する(達成/未達成のチェック表示。責めない):

1. **夜の炭水化物なし**(米・パン・麺)。社会的例外 月3-4回まで
2. **酒なし週3日**(月・水・金推奨)。飲む日は純アルコール25gまで
3. **間食は健康にいい系のみ**(家用4点: ココナッツチップ・チョコ効果72%・デーツ・干し芋/出先: ナッツ・ヨーグルト・ロカボ系等)
4. **生活費 6,000円/日** 記録
5. **朝測定**(絶対。ただし欠測を責めない)

## 6. 体質プロファイル(コーチングロジックに反映)

- **夜糖質耐性が低い**(夜の白米→翌朝体重に即反映、10年データで確定)
- **朝型で安定**するタイプ
- **アーユルヴェーダ: ピッタ体質**(ココナッツ・冷却系が合う。揚げ物・辛味・熱性はピッタ増悪)
- 短期で落とす力は高い(リセット能力あり)
- 弱点: 維持機構、イベント後の自動復帰、静かな増量への鈍感さ
- **非日常イベント**(CC / Heart Reunion / 宿泊 / 出張)で崩れやすい → イベントタグ機能が重要
- 生活制約: 2拠点(秋谷・堀内)、車2台、子供の送り迎え(朝7:30送り・夜21:30迎え)、パートナーの睡眠問題で夜中に起こされる、慢性的睡眠不足

## 8. アプリ要件

### 8.1 必須機能(MVP)

1. **日次エントリフォーム**(スマホ最適化、入力30秒以内)
   - 体重+機種選択(秋谷/堀内トグル)
   - 食事(朝/昼/夜/間食)、酒、運動、通便、睡眠、体感、生活費
   - 途中保存可(朝に体重だけ→夜に食事を追記、が現実の使い方)
2. **ダッシュボード**
   - 体重推移グラフ(堀内基準統一表示、秋谷実測は換算マーク付き)
   - ゾーン帯表示(DANGER≥78 / WATCH 76-78 / PHASE1 73-76 / GOAL 70-72 ※堀内基準に換算して表示)
   - 週平均・月平均(主指標)
   - B運用ルール達成状況(週次: 酒なし日数、夜炭水化物なし日数、生活費)
   - イベントマーカー(CC等をグラフ上に表示)
3. **週次サマリー**(日曜に自動集計)
4. **過去データの閲覧**(日次台帳)

### 8.2 Apple Health 連携(Phase 2 機能)

- WebアプリからHealthKit直接アクセスは不可能
- **iOSショートカット経由**で実装:
  - アプリ側: `POST /api/health-sync` エンドポイント(体重・体脂肪・ワークアウトを受け取る)+ 認証トークン
  - ショートカット側: 毎朝の自動化で「ヘルスケアの最新体重サンプル取得 → HTTPリクエスト」
  - ショートカットのレシピ(手順書)をアプリ内に表示する
- ヘルスケアのエクスポートXML取り込み(過去データ一括)も検討

### 8.3 デザイン指針

- 既存ダッシュボードの世界観を継承: **エディトリアル誌面風**
  - フォント: Fraunces(見出しitalic)+ JetBrains Mono(数値・ラベル)
  - 配色: --ink #1a1a1a / --paper #f4f1ea / --accent #b8412c / --good #4a6741 / --warn #b8862c
  - ダークモード対応(prefers-color-scheme)
  - スマホファースト(ユーザーは平日ほぼスマホ)
- トーンは「淡々と」。祝福バッジ・炎アイコン・streak煽りはしない
- 欠測日は空白として静かに表示

### 8.4 技術スタック(推奨)

- **Cloudflare Workers + D1(SQLite)+ 静的アセット** — ユーザーのCloudflareアカウントが接続済み。無料枠で十分
- フロント: 素のHTML/JS or 軽量フレームワーク(ビルド最小構成を優先)
- 認証: 単一ユーザー想定。シンプルなトークン/パスコードで十分(過剰にしない)
- 代替: ローカル完結ならSQLite+簡易サーバでも可。ただし2拠点+スマホ利用なのでクラウド推奨

## 9. コーチング文言の原則(アプリ内メッセージに適用)

**禁止**: 感情的励まし(「頑張りましょう!」)、根性論、自己否定誘発、数値根拠のない指示、「もっと痩せよう」系の煽り

**推奨**: 観測ベースの淡々とした表示、「ダメな日の報告」を歓迎する空気、単日でなく週平均で語る、体脂肪率の単日変動は無視してよいことの明示

## 12. 申し送り(コーチとして)

- ユーザーは「前進したい」ニーズと「淡々と一生続けたい」思想の両方を持つ。アプリは後者を土台に前者を支える
- 記録が2日空いても、戻ってきたら普通に受け入れる設計に(過去の崩壊パターンは「報告が後ろめたくなる」から始まる)
- 数値はごまかさず、でも責めない。それがこのプロジェクトの生命線
